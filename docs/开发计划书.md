## 一、项目概述

### 1.1 定位

把 iOS 版 WeChatJevPlugin 的产品能力带到 Android，但**实现范式与 iOS 相反**：不注入微信进程、不碰微信任何私有符号，以一个普通 App + 系统无障碍服务「旁挂」在微信旁边——读到屏幕上正在显示的对话 → 调 TypeSafe Jev 原生 API（System One 类型化判断）分析对方真实意图、危险等级、Yes/No 概率与最佳动作 → 生成模型起草候选回复 → 悬浮面板展示 → 一键回填输入框，**发送永远由用户手动点**。

换取的是：免 root、免 TrollStore 类前置条件、微信崩溃面为零（进程外）、封号面最小化（不修改微信本体）。代价是产品形态从「消息流内嵌卡片」退化为「旁挂面板」（v2 可实验气泡锚定卡，见 8.B）。

### 1.2 核心能力清单

1. **消息采集**：无障碍服务读微信聊天页气泡节点，得到「标题 + 谁说的 + 说了什么」；白名单过滤、去重、防抖。
2. **上下文组装**：每会话环形缓冲最近 N 条双向对话，token 预算截断（沿用 iOS 设计）。
3. **AI 分析**：Jev 原生 System One 判断（意图/危险等级/概率/最佳动作）+ OpenAI 兼容生成候选回复（沿用 iOS 实测配置）。
4. **悬浮面板**：悬浮球 + 展开分析面板（v1 主形态）；OCR 兜底（无障碍树读不到正文时截屏离线识别）。
5. **一键回填**：候选回复经 `ACTION_SET_TEXT` 填入微信输入框（失败退剪贴板 + `ACTION_PASTE`），**不自动发送**。
6. **设置页**：接口配置、触发模式、会话白名单、缓存管理、权限向导。

### 1.3 范围边界（明确的不做项）

- **不 hook、不 Xposed、不注入、不改微信包、不读微信数据库**——只用系统无障碍服务与截屏。这是本版路线的根本前提。
- **不自动发送任何消息**，绝不点击微信发送按钮；回填输入框后停手。
- **不碰钱**：转账、红包、收款码相关界面元素一律不交互。
- 聊天内容只在分析那一刻发给模型接口，不落盘、不进日志、不进 git。
- 仅限本人设备、本人有权查看的会话的个人研究用途，不商用。
- 不设计对抗微信无障碍混淆之外的安全检测（伪装服务是「让服务被正常对待」的兼容手段，微信版本更新可能失效，如实计入风险）。

## 三、总体路线与 P1 探针门禁

### 3.1 路线（已定，不再分叉）

```
独立 App（Kotlin）
  ├─ 无障碍服务（伪装 SelectToSpeakService）──读微信聊天页节点
  │     └─ 读不到正文时 → takeScreenshot + ML Kit 离线 OCR 兜底
  ├─ Jev 分析（SystemOne 原生，iOS 同款）+ 候选生成（OpenAI 兼容）
  ├─ 悬浮面板（悬浮球 + 展开卡）──TYPE_ACCESSIBILITY_OVERLAY 免悬浮窗权限（4.2）
  └─ 回填（ACTION_SET_TEXT / 剪贴板+PASTE）──用户点击才动，绝不发送
```

### 3.2 P1 探针门禁（唯一的前置验证，A/B 对照 probe_spec）

**唯一目的**：在**用户自己的设备 + 锁定的微信版本**上，回答两个问题——①伪装服务能不能读到微信聊天节点？②`takeScreenshot()` 能不能拿到微信界面位图？

探针是 App 内一个独立的最小验证模块（只读只打印）：

1. **A/B 对照**（证明「伪装」是有效变量，两组代码逻辑完全一致，仅类名与注册信息不同）：

| 组 | 服务类全名 | 说明 |
|---|---|---|
| 实验组 | `com.google.android.accessibility.selecttospeak.SelectToSpeakService` | 伪装 |
| 对照组 | 本包普通命名服务 | 基线 |

2. **dump 功能**：注册广播 `com.wechatjev.android.DUMP`，`adb shell am broadcast` 触发对 `rootInActiveWindow` 全树遍历，记录每节点 `className / viewId / text / contentDesc / packageName / bounds / isEditable`，输出 JSON 到私有目录 + 摘要打 logcat（tag `JevProbe`：节点总数、有文本节点数、前 10 条文本各截 10 字）。
3. **四组矩阵**：伪装/普通 × 微信聊天页/系统设置页（后者证明服务本身是好的）。

**判定**：
- **PASS**：实验组在微信聊天页节点数 >20 且能看到气泡中文文本（对照组在微信页预期为空根——正好构成证据）→ 进 M1。
- **FAIL**：换变量重测一轮（换微信版本 / 检查服务配置）；仍不过 → 评估当前微信版本是否已堵伪装，回退方案=锁定旧版本微信，或以 OCR 全量兜底形态立项（降级评审，用户拍板）。
- 同时验证 `takeScreenshot`（存 PNG 非全黑）→ 决定 M5 OCR 兜底可行性。

**探针红线**：只读，不 `performAction`，不碰钱，不自动发送，dump 不出本机。探针模块验证通过后归档保留（P2 复验与版本适配复查都用它）。

## 四、技术选型与环境

| 用途 | 选型 | 说明 |
|---|---|---|
| 语言 | Kotlin，传统 View + XML（**不用 Compose**） | 技术栈成熟稳定，工程风险低 |
| 构建 | Gradle + AGP，Windows 本机出包；minSdk 30 / target & compile 35 | takeScreenshot 需 API 30+ |

| 测试 | core 层纯 JVM 单测 + `tools/mock_llm.py` 复用 | Prompt/解析/缓冲不依赖真机回归 |
| 保活 | 前台服务 + 通知；README 指导自启动/省电无限制（小米必做） | 不过度对抗，如实记录已知限制 |

**目标机**：任意 Android 11+ 真机（免 root）。建议测试机与日常机分离仍可选，但本路线不修改微信，风险等级允许日常机直装；用机由用户在 M0 指定并记录。

**版本锁定**：M0 锁定真机微信版本（基线参照 8.0.78，以实际为准），关闭自动更新，记录精确 build 号。微信升级 = 一次显式的适配复验任务（P1 探针回归 + 适配器修正），不随手升。

## 五、总体架构

```
┌────────────────────────────────────────────────────────────┐
│  UI 层 (ui/)            FloatingBall / AnalysisPanel        │
│                         SettingsActivity / 权限向导          │
├────────────────────────────────────────────────────────────┤
│  分析层 (core/)          SystemOneClient(Jev 原生判断)       │
│                         LLMClient(OpenAI 兼容生成)           │
│                         PromptTemplate / Parser / Cache      │
│                         SessionContext(环形缓冲+token 预算)  │
├────────────────────────────────────────────────────────────┤
│  采集层 (capture/)       ChatCaptureService(无障碍服务,按前台 │
│                         包名分发) + ChatAppAdapter(一 App 一 │
│                         适配器) + ocr/(截屏+ML Kit 兜底)      │
├────────────────────────────────────────────────────────────┤
│  回填 (input/)           FillIn: SET_TEXT → 剪贴板+PASTE     │
└────────────────────────────────────────────────────────────┘
```

**一次分析的数据流**：微信前台 → 服务按包名分发到微信适配器 → `extract(root)` 得「标题+消息列表」（契约见 6.1）→ 过滤（白名单/去重/防抖）→ 环形缓冲 → 触发判定（手动默认/自动含 30s 防抖+每日 50 次上限+长度阈值）→ SystemOne 判断 + 候选生成 → 面板展示 → 用户点候选 → 定位输入框节点回填 → **用户手动发送**（发送后的新消息经采集回流缓冲，闭环）。

**适配器架构**（已验证设计）：`ChatAppAdapter` 只负责把当前窗口变成「标题 + 消息列表（side: me/other, text）」，下游全部通用；新增一个 App = 实现一个适配器 + 分发表加一行。v1 只做微信适配器，QQ/X/飞书按 2.1-5 的已知成本列为可选扩展。

## 六、公共契约（开工前定死，跨阶段复用，改名=全量回归）

### 6.1 适配器契约（M1 核心，纪律级别）

```kotlin
interface ChatAppAdapter {
    val pkg: String
    fun extract(root: AccessibilityNodeInfo, screenW: Int): ChatSnapshot? // null=不在聊天窗; 消息列表空=在聊天窗但树里没正文
}
data class ChatSnapshot(val title: String, val messages: List<Msg>)
data class Msg(val side: Side, val text: String)   // Side.ME / Side.OTHER
```

- 返回 `null` = 不在聊天窗（服务静默）；返回**空消息列表** = 在聊天窗但读不到正文 → **只有这一种情况触发 OCR 兜底**。
- 判「在不在聊天窗」一律看树内特征节点（如输入框），**不看 Activity 名**（微信/QQ 均单 Activity 架构）。

### 6.2 配置字段（`core/Config.kt`，沿用三路继承设计）

```
// 判断接口（Jev）：provider = "systemone"(默认, api.typesafe.ai/v1/systemone) | "openrouter"(alpha/decisions) | "custom"
judgeProvider / judgeBaseUrl / judgeKey / judgeModel
// 回复接口（OpenAI 兼容）：留空自动继承 judgeKey
replyBaseUrl / replyKey / replyModel        // 默认 deepseek/deepseek-chat-v3.1
// 触发
triggerMode(manual|auto) / autoDebounceMs(默认30000) / autoDailyCap(默认50) / autoMinLen(默认6)
// 会话与上下文
sessionWhitelist(按会话标题) / contextTokens(默认2500) / contextHistoryCount(默认30)
// 采集与 OCR
ocrFallback(true) / ocrForUnknownApps(false) / ocrAutoAnalyze(false)   // OCR 自动分析默认关，手动点
// 展示
panelOpacity / overlayMode(panel)          // bubble-anchor 为 v2 实验预留
```

### 6.3 事件契约

采集层通过进程内事件总线发 `CaptureEvent(sessionTitle, messages, source)`；分析层订阅。服务与 UI 之间只经事件与结果表交互（结果以「会话标题+最新消息指纹」为键，LRU 60 条——对齐 iOS Store 设计）。

## 七、微信适配方案（M1 作业说明）

### 7.1 伪装服务（路线成立的关键机制）

- **原理**：无障碍服务组件标识是「包名/类全名」。本 App 包名（如 `com.wechatjev.android`）+ 类全名注册成 `com.google.android.accessibility.selecttospeak.SelectToSpeakService`，与系统 TalkBack 包下同名类不冲突、可共存。假设前提：微信只比对类名字符串，不校验包名与签名——已在微信 8.0.78 真机实测成立，P1 在本机复验。
- 服务配置：`canRetrieveWindowContent="true"`、`canTakeScreenshot="true"`（M5 用，**改配置必须重开无障碍才生效**）、`flagReportViewIds | flagRetrieveInteractiveWindows | flagIncludeNotImportantViews`、`accessibilityEventTypes="typeAllMask"`、`notificationTimeout=100`、**不限定 `packageNames`**（限定了就测不出「微信挡我」还是「服务没起来」，且后续要多平台）。
- **绝不使用 `TalkBackService` 类名**（小米常驻朗读，2.1-3）。

### 7.2 微信适配器要点

- 聊天窗判定：树内找输入框（`EditText` 且在页面下部）等特征节点。
- 气泡读取：`id/bkl`（8.0.78 基线，实际以 P1 dump 为准）；「我/对方」按气泡 bounds 在屏幕左/右半边判。
- 会话标题：顶部标题节点；过滤瞬态标题（连接中提示等会污染会话记录，实测踩过此坑，加稳定性判定——连续两帧一致才认）。
- 列表页防误触：会话列表页结构与聊天页相似，必须先过「聊天窗判定」再提取。
- 版本漂移预案：节点 id 随版本可能变（`bkl` 是混淆名）；适配器内做「配置化 id + 运行时探测兜底（按气泡类名+左右布局特征找）」，id 表与代码分离，微信升级只改配置。

## 八、工程红线（A/B 分类，制度沿用 iOS 版）

### A. 安全与稳定类（不可破）

1. **只读采集**：不对任何微信节点 `performAction`。唯一例外=回填输入框的 `ACTION_SET_TEXT` / `ACTION_PASTE`，且**仅响应用户对候选回复的点击**，绝不自动执行。
2. **绝不自动发送**：永不 `ACTION_CLICK` 发送按钮/发送节点；回填后停手。
3. **不碰钱**：转账、红包、收款码相关界面元素绝不交互（包含 OCR 路径——识别到支付类界面直接放弃该帧）。
4. 密钥不落盘（私有空间除外）、不进日志、不进 git；聊天内容只在分析时刻发给接口，不落盘不进日志。
5. OCR 纪律：全局限频 ≥1s + 指数退避（1→2→4→8→16→30s 封顶）+ 屏幕签名去重防连拍；截屏前隐藏自身悬浮窗、回调里立刻转存并释放 HardwareBuffer。
6. 服务工程纪律：UI 全部主线程；事件回调最小逻辑快速返回（重活 post 出去）；服务生命周期内注册的接收器/监听器必须成对释放；崩溃只允许崩自己（进程外天然隔离，但要做「服务崩溃自动拉起 + 面板提示」而不是静默失效）。
7. 适配器契约纪律：`null` 与「空列表」语义绝不能混（6.1），违反会引发 OCR 误连拍或采集静默失效。

### B. 保守策略类（用户授权后可破，破前先立验收）

- ~~只做悬浮面板~~ → **气泡锚定分析卡**（v2 实验）：以 `TYPE_ACCESSIBILITY_OVERLAY` 窗口 + 气泡节点 bounds 定位，把分析卡贴在目标气泡下方，监听滚动事件/短轮询跟随。这是无障碍路线下最接近 iOS 内嵌卡片形态的方案；已知风险：滚动跟随精度、性能、遮挡。**先做技术验证单独评审，不过就退回面板形态**。
- ~~只做手动触发~~ → 自动分析（30s 防抖 + 每日 50 上限 + 长度阈值，参数沿用 iOS 已验证值）。
- ~~只做微信~~ → QQ / X / 飞书适配器（成本已知：各一个几十行适配器 + 真机验证；飞书型直接走 OCR）。

## 十、验收体系与执行协议

### 10.1 四级验收尺子（每个任务的出口，建者不自证、贴真实输出）

- **A 构建**：`gradlew assembleDebug` 零 error，产物存在。
- **B 探针**：P1 可读性裁定报告 PASS（一次性门禁；微信版本变更时重跑）。
- **C 校准**（M2 一次性）：iOS 题目集/Schema 已实测，默认豁免；若改题目措辞，启用 `tools/jev/` 校准脚手架（标注集 ≥25 条中文对话、danger_level MAE <1.0 档、意图/需求命中率 ≥60%，最多迭代 3 轮）。
- **D 真机冒烟**（M6 前完整一遍）：对方新消息→面板出分析 ≤3s；候选 ≥2 条已排序；回填未发送；自己发言不触发；切会话重置；密钥不进 logcat；断网给可读错误；静默 10 分钟零调用；杀进程重开后全链路自愈。

### 10.2 多会话执行协议（ZCode 适配版）

- **角色**：用户=主控+真机操作手；ZCode 会话=执行者；关键阶段另开只读会话评审。
- **单写者**：同一时间只一个会话改代码；上一任务构建通过才派下一个。
- **报告制度**：每任务写 `_reports/<任务名>_report.md`（gitignore）：做法与证据 → 逐文件改动 → 验收命令**真实输出原文** → **自验缺口**。
- **夜码晨验**：手机不在时推进到「构建通过 + 单测过 + 缺口列明」，真机验收留清单执行。
- **跨边界只报告不改**；**禁 `git commit`/`git push`** 由用户拍板。
- **Windows 工程纪律**：gradle/配置一律 Edit 工具改；UTF-8；路径全 ASCII。

| 目录 | 归属 | 说明 |

## 十一、成本与延迟预算（沿用 iOS 实测）

## 十二、风险与对策

### 12.1 伪装失效风险（路线特有，中）

微信版本更新可能校验包名/签名使伪装失效。对策：P1 探针保留为回归工具，微信升级先跑探针再升；失败则评估旧版本锁定或 OCR 全量兜底降级形态。**不设计进一步的对抗**（超出个人研究边界，收益低）。

### 12.2 账号风险（低，如实评估）

本路线不修改微信、不注入、行为特征仅为「开启无障碍 + 前台服务」，为系统正常使用范畴；服务端行为风控视角下无发送行为改变（永不代发）。仍建议初期小号体验 1 周，且自动模式默认关。

### 12.3 隐私风险

同 iOS：上传上下文含对方消息；优先选不训练不留存接口；缓存仅私有空间；OCR 全离线；设置页一键清空。

### 12.4 版本与机型漂移

节点 id 漂移（混淆名随版本变）：配置化 id 表 + 特征探测兜底（7.2）；机型差异（分辨率/左右阈值）：判边用相对比例不用绝对像素。国产 ROM 后台冻结：如实写已知限制 + 向导配自启动/省电，不过度对抗。

### 12.5 产品形态差距（对齐预期）

无障碍路线做不到 iOS 的真内嵌卡片；v2 的气泡锚定卡是实验性逼近，验收不过就停留在面板形态——这是路线选择时已知并接受的代价。
